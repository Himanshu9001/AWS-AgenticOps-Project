Here is the standard procedure for handling critically high CPU utilization on an EC2 instance:
---
## 🔴 Severity Classification
| CPU % | Duration | Severity | Response Time |
|---|---|---|---|
| 85–90% | 5 min | Medium | 30 minutes |
| 90–95% | 5 min | High | 15 minutes |
| **>95%** | **2 min** | **Critical** | **Immediate** |
---
## 🔍 Diagnosis Steps
1. **Identify the Affected Resource** — Check CloudWatch alarms (alarm name pattern: AgenticOps-HighCPU-{instance-id}) and gather instance details (ID, type, state).
2. **Check CloudWatch Metrics** — Pull CPU utilization stats for the last 30 minutes to understand trend and severity.
3. **SSH & Investigate Processes** — Run top, ps aux --sort=-%cpu, and uptime to identify the runaway process. Also check memory/swap with free -m and vmstat.
4. **Check Application Logs** — Look for errors in app logs and OOM killer activity in dmesg.
---
## 🛠️ Remediation Actions (in order of preference)
| Action | When to Use | Risk |
|---|---|---|
| **Kill Runaway Process** | Specific process identified as the culprit | Possible data loss if it's mid-write — confirm with app owner |
| **Restart Application Service** | App process is misbehaving but instance is responsive | Brief service interruption |
| **Scale Out (Horizontal)** | Traffic spike, instance part of an ASG | Low risk, increases capacity |
| **Scale Up (Vertical)** | Instance is chronically under-provisioned | ~2–5 min downtime, requires stop/start |
---
## ⚠️ Key Lessons from Past Incidents
- **Never use cpu_count() without an explicit cap** in multiprocessing code — always set MAX_WORKERS via an environment variable.
- **Burstable instances (t3.*)** are **not suitable for sustained CPU workloads** — use compute-optimized types (e.g., c6i, c7g) for batch jobs.
- **Bulk jobs should go through SQS** to rate-limit processing and protect the instance.
---
## 📞 Escalation Path
1. **L1 (On-call):** Kill runaway process or restart the application service.
2. **L2 (Senior Engineer):** Scale out ASG or scale up instance type.
3. **L3 (Architect):** If issue recurs within 24 hours → capacity planning review.

- **Concurrency limit hit?** → Increase the reserved concurrency for agenticops-async-consumer.

## Important SQS Configuration to Verify
A common misconfiguration that can cause tasks to appear "stuck" or trigger **duplicate executions** is a mismatched visibility timeout. The SQS visibility timeout **must be greater than the Lambda timeout**:
| Parameter | Expected Value |
|---|---|
| Visibility timeout | **330 seconds** (Lambda timeout 300s + 30s buffer) |
| Message retention | 4 hours |
| Max receive count | 3 (then routes to DLQ) |
| DLQ | agenticops-async-tasks-dlq |
If the visibility timeout is too short, messages re-appear in the queue before Lambda finishes, causing both duplicates and the appearance of tasks stuck in queued. Fix with:
bash
aws sqs set-queue-attributes \
  --queue-url https://sqs.us-east-1.amazonaws.com/ACCOUNT/agenticops-async-tasks \
  --attributes VisibilityTimeout=330

## 🚨 RDS Connection Exhaustion — What To Do
### Overview
RDS connection exhaustion occurs when the `DatabaseConnections` metric hits the `max_connections` limit, causing new connections to fail with errors like `Too many connections`. This is a **P0/Critical** incident.
**Alert Thresholds:**
| Threshold | Action |
|---|---|
| > 60% of `max_connections` | ⚠️ Warning — monitor closely |
| > 85% | 🔴 Critical — act immediately |
| > 95% | 💀 P0 Emergency |
**Max Connections by Instance Class:**
| Instance Class | max_connections |
|---|---|
| db.t3.micro | 66 |
| db.t3.medium | 312 |
| db.r6g.large | 1,365 |
| db.r6g.xlarge | 2,730 |
| db.r6g.2xlarge | 5,460 |
---
## 🔍 Step-by-Step Diagnosis
**Step 1 — Check current connection count via CloudWatch:**
```bash
aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name DatabaseConnections \
  --dimensions Name=DBInstanceIdentifier,Value=<your-db-id> \
  --start-time $(date -u -d '15 minutes ago' +%Y-%m-%dT%H:%M:%SZ) \
  --end-time $(date -u +%Y-%m-%dT%H:%M:%SZ) \
  --period 60 \
  --statistics Average,Maximum
```
**Step 2 — Inspect active connections on the DB:**
```sql
-- Count connections by state
SELECT state, count(*) FROM pg_stat_activity GROUP BY state;
-- Connections by application, user, and client
SELECT usename, application_name, client_addr, state, count(*)
FROM pg_stat_activity
GROUP BY usename, application_name, client_addr, state
ORDER BY count DESC;
-- Long-running queries (> 5 minutes)
SELECT pid, now() - pg_stat_activity.query_start AS duration, query, state
FROM pg_stat_activity
WHERE (now() - pg_stat_activity.query_start) > interval '5 minutes'
AND state != 'idle';
```
